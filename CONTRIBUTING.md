# Руководство контрибьютора Красава!

Спасибо за интерес к проекту! **Красава!** — кроссплатформенное приложение
расписания РТУ МИРЭА на Kotlin Multiplatform и Compose Multiplatform
(Android + iOS). Этот документ описывает правила работы с ветками, стандарты кода,
процесс тестовых сборок и создания Pull Request.

Актуальные планы разработки — в [ROADMAP.md](ROADMAP.md).

---

## 1. Основные принципы

1. **Одна задача — одна ветка.** Не смешивайте в одной ветке несвязанные изменения.
2. **Проверяйте на устройстве.** Перед созданием PR соберите тестовый APK/IPA
   через CI (раздел 4) и проверьте работу на реальном телефоне.
3. **Никаких секретов в репозитории.** Токены, пароли и личные ключи в коммиты
   не попадают никогда.
4. **Минимализм (YAGNI).** Предпочитайте стандартные возможности KMP и Compose
   сторонним тяжёлым библиотекам. Новая зависимость — только с обоснованием в PR.
5. **Приватность.** Приложение не передаёт идентифицирующие данные пользователя.
   Не добавляйте в аналитические события имена, номера групп, идентификаторы
   расписаний или содержимое пользовательских данных.

## 2. Работа с ветками

### 2.1. Создание ветки

Новая ветка всегда создаётся от актуального `main`:

```bash
git checkout main
git pull origin main
git checkout -b <тип>/<краткое-описание>
```

### 2.2. Именование веток

Формат: `<тип>/<описание-в-kebab-case>`

| Префикс | Назначение | Примеры |
| :--- | :--- | :--- |
| `feat/` | Новая функциональность | `feat/widget-next-lesson` |
| `fix/` | Исправление ошибок | `fix/android-map-zoom` |
| `refactor/` | Изменение структуры без смены поведения | `refactor/schedule-repository` |
| `docs/` | Документация | `docs/contributing-guide` |
| `perf/` | Оптимизация производительности | `perf/compose-lazy-column` |

Не используйте бессмысленные имена (`patch1`, `test`, `temp`, `my-branch`),
заглавные буквы, пробелы и подчёркивания.

## 3. Стандарты кода

### 3.1. Kotlin Multiplatform и Compose

- Общая логика, модели и экраны живут в `shared/src/commonMain/kotlin`;
  платформенные реализации — в `androidMain` / `iosMain` и нативных хостах.
- **`runBlocking` на UI-потоке запрещён.** Используйте корутины:
  `Dispatchers.Default` для вычислений, `Dispatchers.IO` для ввода-вывода.
- Состояние Compose — через `remember` / `rememberSaveable` и `StateFlow`
  из ViewModel; избегайте лишних рекомпозиций.
- Версии в коде не хардкодятся: в репозитории хранится только
  `AppVersion.RELEASE_VERSION` (линия разработки), полные версии и номера
  сборок подставляет CI.

### 3.2. Векторные карты (SVG)

Карты приложения: `shared/src/commonMain/composeResources/files/maps/<campus>/`;
рабочие материалы — в `maps/`. При редактировании планов этажей:

- SVG обязан оставаться валидным XML (проверка через `ElementTree`).
- Сохраняйте структуру слоёв: `#walls`, `#room-polygons`, `#room-labels`,
  `#markers`.
- Большая аудитория — один объединённый контур, а не несколько смежных
  полигонов: при клике должна подсвечиваться вся аудитория.
- Лестницы содержат `aria-label="Лестница на Этаж N"` — скрипт переключения
  этажей ориентируется на этот атрибут.
- После правки выполните smoke-check карты на устройстве.

## 4. Тестовая сборка своей ветки

Для проверки ветки используется изолированный сборщик
**`🧪 Contributor Test Build (APK & IPA)`** (`.github/workflows/build-test-branch.yml`).
Он собирает APK и IPA **только в артефакты запуска**: ничего не публикует
в Releases, не трогает теги и `gh-pages`.

1. Отправьте ветку на GitHub:
   ```bash
   git push -u origin <ваша-ветка>
   ```
2. В репозитории откройте вкладку **Actions** → **🧪 Contributor Test Build
   (APK & IPA)** → **Run workflow**.
3. Заполните параметры:
   - **Use workflow from** — ваша ветка (или `main`, если ветка уже подтянута);
   - **Ветка для сборки** — имя ветки (например, `fix/android-map-zoom`);
   - отметьте нужные платформы: **Build Android APK** / **Build iOS IPA**.
4. Дождитесь завершения (Android ~2–3 минуты, iOS ~15–20 минут).
5. Скачайте установочные файлы из секции **Artifacts** внизу страницы запуска:
   - `Schedule-test-<slug>-APK` — Android;
   - `Schedule-test-<slug>-IPA` — iOS (unsigned; устанавливается через
     GBox, Scarlet, Sideloadly и аналогичные клиенты с переподписанием).
6. Проверьте изменения на реальном устройстве.

## 5. Создание Pull Request

### 5.1. Автоматический аудит и PR (для участников с доступом к Actions)

1. Отправьте ветку: `git push -u origin <ваша-ветка>`.
2. Вкладка **Actions** → **🔍 Review Branch vs Main** → **Run workflow**:
   - **Ветка для анализа** — имя вашей ветки;
   - `create_pr` оставьте включённым (по умолчанию).
3. Скрипт `tools/branch_reviewer.py` детерминированно проанализирует diff,
   проверит чеклист безопасности и архитектуры KMP, сформирует заголовок
   по Conventional Commits и **создаст или обновит Pull Request в `main`**
   с подробным описанием. Ссылка на PR появится в Summary запуска.

### 5.2. PR вручную (для форков и внешних контрибьюторов)

1. Вкладка **Pull requests** → **New pull request**.
2. **base** — строго `main`, **compare** — ваша ветка.
3. Заголовок — по Conventional Commits:
   `fix(map): move room info card below campus header`.
4. В описании укажите:
   - **Что сделано** — ключевые изменения по пунктам;
   - **Зачем** — какую проблему решает PR;
   - **Тестирование** — на каких платформах и как проверялось.
5. После создания PR бот-аудитор автоматически оставит отчёт в комментариях.

## 6. Как устроены релизы

- Контрибьюторам **не нужно** менять номера версий/сборок или выпускать релизы.
- Push в `main` собирает только тестовую rolling-сборку
  (`🚧 Main Preview Build`), которая обычным пользователям не видна.
- Официальный релиз — это git-тег, который ставит maintainer:
  `v26.2.0` (стабильный), `v26.2.1` (патч), `v26.2.0-beta.N` / `-rc.N`
  (предварительные). Релизный сборщик `🚀 Release Mobile (Tag v*)` сам
  подставляет версию и номер сборки, публикует GitHub Release и обновляет
  ленты обновлений на `gh-pages`.
- Схема версионирования — CalVer `ГГ.РЕЛИЗ.ПАТЧ` (например, `26.2.0` —
  вторая релизная линия 2026 года); в репозитории хранится только линия
  разработки, полные версии каналов подставляет CI.

## 7. Сообщения об ошибках и предложения

- Баги и предложения оформляйте через
  [Issues](https://github.com/Vibe-Moments-Technologies/krasava-app/issues) с помощью шаблонов:
  баг-репорт, предложение функции, вопрос, проблема с данными расписания.
- Прежде чем создать Issue, проверьте существующие — бот первичного анализа
  помогает находить дубликаты.
- Неактивные тикеты автоматически помечаются через 60 дней и закрываются
  через 7 дней тишины; если проблема всё ещё актуальна — просто прокомментируйте.
