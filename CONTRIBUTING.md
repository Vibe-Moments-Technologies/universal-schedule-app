# Руководство контрибьютора

Спасибо за интерес к проекту! **«Расписание» (universal-schedule)** — кроссплатформенное
**полностью офлайн**-приложение расписания на Kotlin Multiplatform и Compose
Multiplatform (Android + iOS). Студент сам собирает семестр во встроенном
конфигураторе; сервера с расписанием нет — приложение подходит любому учебному
заведению.

---

## 1. Основные принципы

1. **Одна задача — одна ветка.** Не смешивайте в одной ветке несвязанные изменения.
2. **Проверяйте на устройстве.** Перед созданием PR соберите тестовый APK/IPA
   через CI (раздел 4) и проверьте работу на реальном телефоне.
3. **Никаких секретов в репозитории.** Токены, пароли и личные ключи в коммиты
   не попадают никогда.
4. **Минимализм (YAGNI).** Предпочитайте стандартные возможности KMP и Compose
   сторонним тяжёлым библиотекам. Новая зависимость — только с обоснованием в PR.
5. **Офлайн прежде всего.** Расписание, задачи и заметки не должны зависеть от
   сети. Единственный сетевой запрос приложения — проверка обновлений (GitHub).
6. **Приватность.** Не добавляйте в аналитические события имена, номера групп,
   названия предметов или содержимое пользовательских данных.

---

## 2. Работа с ветками

Новая ветка всегда создаётся от актуального `main`:

```bash
git checkout main
git pull origin main
git checkout -b <тип>/<краткое-описание>
```

Формат: `<тип>/<описание-в-kebab-case>`

| Префикс | Назначение | Примеры |
| :--- | :--- | :--- |
| `feat/` | Новая функциональность | `feat/configurator-bells` |
| `fix/` | Исправление ошибок | `fix/week-parity` |
| `refactor/` | Изменение структуры без смены поведения | `refactor/schedule-repository` |
| `docs/` | Документация | `docs/contributing-guide` |
| `perf/` | Оптимизация производительности | `perf/compose-lazy-column` |

Не используйте бессмысленные имена (`patch1`, `test`, `temp`, `my-branch`),
заглавные буквы, пробелы и подчёркивания.

## 3. Стандарты кода

- Общая логика, модели и экраны живут в `shared/src/commonMain/kotlin`;
  платформенные реализации — в `androidMain` / `iosMain` и нативных хостах.
- **`runBlocking` на UI-потоке запрещён.** Используйте корутины:
  `Dispatchers.Default` для вычислений, `Dispatchers.IO` для ввода-вывода.
- Состояние Compose — через `remember` / `rememberSaveable` и `StateFlow`
  из ViewModel; избегайте лишних рекомпозиций.
- Формат расписания — `SemesterConfig` (`data/model/SemesterConfig.kt`),
  spec: [docs/SCHEDULE_FORMAT.md](docs/SCHEDULE_FORMAT.md). Любые изменения
  формата — только с сохранением обратной совместимости импорта
  (`ignoreUnknownKeys`) и обновлением спеки.
- Версии в коде не хардкодятся: в репозитории хранится только
  `AppVersion.RELEASE_VERSION` (линия разработки), полные версии и номера
  сборок подставляет CI.

## 4. Тестовая сборка своей ветки

Для проверки ветки используется изолированный сборщик
**`🧪 Contributor Test Build (APK & IPA)`** (`.github/workflows/build-test-branch.yml`).
Он собирает APK и IPA **только в артефакты запуска**: ничего не публикует
в Releases, не трогает теги и `gh-pages`.

1. Отправьте ветку на GitHub: `git push -u origin <ваша-ветка>`.
2. Вкладка **Actions** → **🧪 Contributor Test Build (APK & IPA)** → **Run workflow**.
3. Заполните параметры: ветка для сборки и нужные платформы.
4. Дождитесь завершения (Android ~3–5 минут, iOS ~15–20 минут).
5. Скачайте установочные файлы из секции **Artifacts** и проверьте на устройстве.

---

## 5. Создание Pull Request

1. Вкладка **Pull requests** → **New pull request**.
2. **base** — строго `main`, **compare** — ваша ветка.
3. Заголовок — по Conventional Commits: `fix(configurator): week range validation`.
4. В описании укажите:
   - **Что сделано** — ключевые изменения по пунктам;
   - **Зачем** — какую проблему решает PR;
   - **Тестирование** — на каких платформах и как проверялось.

---

## 6. Как устроены релизы

- Контрибьюторам **не нужно** менять номера версий/сборок или выпускать релизы.
- Push в `main` собирает rolling-сборку (`🚧 Main Preview Build`) в
  prerelease `preview` — обычным пользователям она не видна.
- Официальный релиз — git-тег, который ставит maintainer: `v26.0.0`
  (стабильный), `v26.0.1` (патч). Релизный сборщик `🚀 Release Mobile (Tag v*)`
  сам подставляет версию и номер сборки (`tools/versioning.py`), публикует
  GitHub Release и обновляет ленту обновлений `version.json` на `gh-pages`.
- Схема версионирования — CalVer `ГГ.РЕЛИЗ.ПАТЧ` (например, `26.0.0` —
  первая релизная линия 2026 года).
